## Email verification delivery investigation

The application loaded the configured Gmail values from the private `device_monitoring_prototype\.env`: `smtp.gmail.com`, port 587, TLS enabled, a configured SMTP username/password, and a default sender matching the authenticated Gmail account. The password value was checked for presence only and was not displayed. `check-mail` completed STARTTLS authentication, and a real, randomly coded verification message submitted through the application mail sender to the configured sender Gmail address was accepted by Gmail's SMTP server. No SMTP authentication or recipient-refusal error was returned. Because the mailbox is not available to this QA run and no separate registering Gmail address was provided, actual inbox placement (Inbox, Spam, or provider filtering) and end-to-end verification by an external recipient cannot be confirmed. SMTP acceptance means handoff to Gmail, not proof of inbox arrival; the remaining delivery issue is downstream of application SMTP submission unless a recipient-side rejection can be reproduced.

The workflow audit confirmed that registration validates the email, stages the password hash and challenge, generates a six-digit cryptographically random code, HMAC-hashes it in the database with a five-minute expiry, then sends it before the popup advances. Verification is bound to the session challenge/email, checks expiry and attempt limits, marks the verification used, and only then allows authenticator setup and final account creation. The review found a retry defect: when the initial SMTP send failed, its persisted challenge remained active with its initial 60-second resend cooldown, preventing an immediate retry; failure details also lacked enough safe operational context. The fix expires the unsent code, resets the initial-send counter/cooldown so the popup can retry immediately, and enforces the cooldown/quota for subsequent failed resend attempts. Gmail sender mismatch and malformed recipient/code are now rejected; outgoing mail is a branded text+HTML multipart message with the six-digit code and five-minute expiry notice. SMTP acceptance/refusal, registration rejection, invalid/expired code, authenticator failure, and success events are logged without logging passwords, SMTP credentials, email codes, or recipient addresses.

QA covered the registration popup/API path, mocked SMTP TLS/send and refusal/auth failures, malformed and mismatched sender configuration, immediate resend after initial delivery failure, resend cooldown and invalidation, wrong/expired/reused codes, and delayed account creation. The live checks confirmed environment loading, SMTP TLS/authentication, and SMTP acceptance of one real message to the configured Gmail account. The message's presence in the mailbox and delivery to a different registrant's Gmail inbox remain **unverified**; inspect Inbox and Spam and repeat with an explicitly authorized test recipient to establish final inbox delivery.

## Database connectivity investigation and recovery

The reported “Database connection or setup required. The database schema is incomplete.” message was caused by schema drift, not an unavailable MySQL server or rejected credentials. The app successfully connected to MariaDB 10.4.32 at `localhost:3306/devmonitor`; `SELECT DATABASE(), CURRENT_USER(), VERSION()` returned the expected database/server and `root@localhost`. The configured account exists and had global privileges. `.env` was present, `DATABASE_URL` was unset, and its host, port, user, and database matched the live target. The configured local root password is empty, consistent with this XAMPP development installation. The separate Windows `MySQL80` service being stopped was not causal; XAMPP's MariaDB owns port 3306. Gmail SMTP settings are now loaded from the private `.env` and `check-mail` successfully completed STARTTLS authentication.

Read-only `check-db` identified the migration-009 differences: missing `registration_challenges` and seven `users` columns (`email_verified`, `email_verified_at`, `totp_enabled`, `totp_secret_encrypted`, `totp_verified_at`, `totp_last_counter`, and `totp_attempts`). The other expected 16 pre-migration tables were present. Migrations 007 and 008 were already applied. After migration 009, the only remaining mismatch was the missing `email_verifications` table from migration 010. No credential, environment-loading, or connection-pool failure caused the reported message.

Before migration 009, a full logical backup was saved outside the repository and verified to contain all 16 table definitions and data inserts. Pre-migration counts were recorded: 8 users, 4 devices, 4 device specifications, 15 device-registration tokens, 20 device logs, and 84 activity logs. Migration `009_email_and_totp_authentication.sql` was applied once. Post-migration checks found 17 tables, all seven new user columns, and the staged-challenge table; all recorded data counts remained unchanged. `check-db` then validated 13 model indexes, primary/unique keys, foreign keys, check constraints, and no orphaned foreign-key rows.

`init-db` was run after migration 009: it confirmed the existing Administrator account and credentials were preserved, RBAC roles were ready, and the recorded data counts remained unchanged. As designed, `init-db` creates missing tables and seeds missing roles/permissions, but does not add columns or constraints to existing tables. Before migration 010, a new logical backup was saved outside the repository and verified to contain the 17 existing table definitions; a preflight query confirmed the verification table was absent and the prior email default was true. Migration 010 then added `email_verifications` and changed the default for new accounts to false without altering existing rows. Final `check-db` reports 18 tables and 16 indexes; prior account/device/audit counts are unchanged. The configured local `.env` has private Gmail SMTP settings; passwords and email codes are not included in this report.

An optional least-privilege account setup exposed an independent MariaDB system-schema problem: read-only `CHECK TABLE` reports `mysql.db` and `mysql.tables_priv` as corrupt (Aria checksum error); `mysql.global_priv` and other checked privilege tables report OK. `GRANT` therefore failed. The app still uses its verified configured `root@localhost` account; the attempted `devmonitor_app@localhost` account has only `USAGE`, was not placed in `.env`, and is not used by the app. No repair was attempted because the MariaDB system privilege database has not been separately backed up and online repair could affect other accounts. This requires a MySQL-system-database backup and a planned maintenance repair before provisioning a restricted app account.

For future schema recovery, inspect with `check-db`, make a logical backup, apply only migrations absent from the live schema, then rerun `check-db`. Do not reapply one-time `ALTER TABLE` scripts. See `README.md` for backup, migration, and validation commands. Connection and schema failures are reported separately; missing columns/tables should be resolved through migrations, not by dropping or recreating user tables.

## User workflows and validation

- **Account and verification:** submit valid registration fields. The popup sends an email code; the account row remains absent until both email and Google Authenticator codes verify. The authenticator QR is separate from the existing 30-minute device-enrollment QR. Once signed in, the user can issue a device code; its URL is reachable only if the phone can reach the configured app origin (`localhost` will not work from a separate phone).
- **Device and dashboard:** after verification, explicitly confirm trust before downloading the token-bound Windows Python agent. The agent detects and displays supported specifications; the user reviews and approves submission. The server validates and consumes the confirmed one-use token and stores the device, owner, specifications, network address, and event history in one transaction. Device/dashboard/monitoring access is granted after the verified device is linked. Existing authorized device details/history, search/filter, edit, archive/restore, and administrator soft-delete continue under current access rules. A diagnostic scan still adds placeholder history only.
- **Administration:** initialize roles and bootstrap admin, then create/edit/deactivate users, manage existing devices, and query audit events. Administrators do not receive registration controls and cannot register a device through direct API/page requests. User/device authorization is checked by Flask routes, not trusted to the browser.

Integration coverage includes expected success and rejection paths, persisted state, access boundaries, malformed/invalid operations, and missing database/setup handling. Client-side checks are usability aids only; server-side validation and authorization are authoritative.

## Database scope

Updated SQLAlchemy models and `schema.sql` define 18 application tables. Integration tests verify ORM initialization and representative persisted account/challenge, email-verification, device, network, diagnostic, enrollment-token, and audit records. The local MariaDB is now at migration 010 and matches the updated model. Read-only orphan checks after migration found no broken foreign-key records:

| Table(s) | Responsibility |
|---|---|
| `users` | Account identity, unique username/email, password hash, verified-email state, encrypted TOTP secret/state, status, and timestamps. |
| `registration_challenges` | Temporary staged registration, HMAC-hashed email code, expiry, attempt counters, resend limits, and verification timestamps. |
| `email_verifications` | Challenge-linked HMAC digest of the six-digit email code, five-minute expiry, verified/used state, and timestamps; plaintext codes are not stored. |
| `roles`, `permissions` | Role and permission definitions. |
| `user_roles`, `role_permissions` | Many-to-many account-role and role-permission associations. |
| `devices` | Device identity, owner/registrant, verification flag, connectivity status, lifecycle state, and timestamps. |
| `device_registration_tokens` | SHA-256 token hashes, issuing user, expiry, use/revocation timestamps; unique tokens are one-use. |
| `device_specifications` | One-to-one CPU, RAM capacity/usage, storage devices/capacity/availability, GPU, motherboard brand, OS, adapter, and IP inventory. |
| `network_interfaces`, `network_observations` | Interface inventory and timestamped address/connection observations. |
| `network_records` | Timestamped device IP, subnet, gateway, DNS, and connectivity snapshots. |
| `diagnostic_runs`, `diagnostic_checks` | Diagnostic history and per-run check results. |
| `device_metrics` | Historical CPU, memory, storage, and network metrics; collection is not enabled. |
| `activity_logs` | Timestamped account/system actions with optional actor and entity reference. |
| `logs` | Device-linked events such as registration, edits, archiving, and diagnostic history. |

The models and schema define primary/foreign keys, unique usernames/emails/asset tags and associations, status and metric range checks, and query indexes. Devices require an owner and can have one specification plus network history/interfaces, diagnostic runs, metrics, and device logs; diagnostic runs can have multiple checks. The account-role and role-permission association tables implement RBAC. Foreign-key delete behavior retains account ownership constraints, while device-owned history cascades only on physical deletion. Application account deactivation and device archive/restore/soft-delete preserve rows and history. Connectivity status is distinct from active/archived/deleted lifecycle state.

**Database verification boundary:** integration tests use isolated SQLite. The local MariaDB is at migration 010 with 8 users, 4 devices, 4 specifications, 15 QR-token rows, 20 device logs, and 86 activity logs. Verified pre-migration logical backups are stored outside the repository. This does not establish that another machine's credentials, data, or schema are valid. `db.create_all()` creates missing tables but does not update existing ones. Back up existing data and apply only the migrations required for the target schema; see `README.md` and `DATABASE_DESIGN.md`.
